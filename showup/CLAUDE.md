# CLAUDE.md (showup/)

Showup is a free, no-account, code-based screen-share service built on LiveKit (each one is a "showup session" in user-facing text), with the presenter webcam overlay. It lives in this folder of the Nasiha repo for now but is meant to be split into its own repo later.

## Rules for this folder

- **Self-contained.** Never import from `../web/` (or anything outside `showup/`). If you need something from Nasiha, copy it in. This is what keeps the later repo split a plain move.
- **Not Nasiha.** No Clerk, no Prisma/Postgres, no medical/community framing, no Nasiha branding or legal copy. Anonymous users only; there are no accounts.
- **Name: Showup. Domain: `showup.cloudcurio.com`** (decided in Showup 03; see `NAMING.md` for clearance findings and the DNS setup). DNS for `cloudcurio.com` is at Namecheap; the A record for `showup` -> VPS `50.6.224.185` is added during the deploy objective (Showup 05). Read the domain from env (`NEXT_PUBLIC_APP_URL`) rather than hardcoding it.
- **Ports.** Run dev on 3012 (`npm run dev -- -p 3012`). Never bind 3010 (live Nasiha app) or 3011 (where `web/` dev runs).
- **Commits** start with `showup:` and don't mix `showup/` changes with `web/` changes.
- **Planwright:** work is tracked as the "Showup — Standalone Screen-Share Service" initiative in the Nasihaonline project (objectives are numbered "Showup 01".."Showup 10" in build order). The approved plan is `/home/nadeem/.claude/plans/i-want-to-make-composed-dragonfly.md`.

## Layout

- `app/` Next.js App Router: landing page (`page.tsx`), room page (`room/`), API routes (`api/rooms/start`, `api/rooms/join`, `api/health`).
- `lib/livekit.ts` server-only LiveKit helpers (token mint, room service, webhook verify). `lib/room-code.ts` code normalization and room naming.
- `lib/presenter-overlay/compositor.ts` and `components/presenter-overlay-control.tsx` the client-side webcam overlay, copied from Nasiha's `web/`. The overlay is composited in the sharer's browser; no server involvement.
- `components/showup-room.tsx` the in-session screen (LiveKit `VideoConference` plus overlay controls).
- `lib/redis.ts` / `lib/rate-limit.ts` (copied from Nasiha, then adapted): Redis client that tolerates Redis being down, and the rate limiter. `lib/room-state.ts` holds the `showup:room:{digest}` code claims (SET NX, hostSecret reclaim). Routes catch dependency failures and answer 503 + Retry-After (`unavailableResponse`), never a 500. `api/webhooks/livekit` frees a code on `room_finished`. `api/health` always returns 200 with per-dependency status.
- Recording (Showup 06): `lib/livekit-egress.ts` (start/stop/status), `lib/recordings.ts` (Redis hash per recording; hostSecret/passcode auth; reconcile with LiveKit so it works even if the webhook never arrives), `lib/recordings-storage.ts` (egress writes to the internal `MINIO_ENDPOINT`, downloads are presigned for `MINIO_PUBLIC_ENDPOINT`), `lib/recording-email.ts` (Resend). Routes: `api/rooms/recording` (host start/stop), `api/recordings/[recId]` (status + links), `api/recordings/lookup` (code + passcode), `api/recordings/[recId]/email`. Pages: `/recording/[recId]` (exit screen + recovery link), `/recover`. Never let a route return recording details without the hostSecret or matching passcode; unknown id and wrong secret must look identical (404).
- Participant list (Showup 24): the "People (N)" button at the top of the top-left stack (`components/participant-list.tsx`) opens a list of everyone in the room by name, camera on or off, with (you) and Host tags, mic/camera state and a speaking pulse; on the host's view co-ghost guests on the overlay are tagged "On the share" (a guest shown only by follow-the-speaker is not, since that isn't in `overlayIds`). The pure logic is `lib/participants.ts` (`buildRoster`: you first, then the host, then by name; unnamed = "Guest"; the host is read from the server-minted token metadata `{role:"host"}`, never from the display name; lobby roles excluded). It reads LiveKit's own room state (events plus a 2 s safety poll, standard participants only, so recorders aren't listed); nothing is sent, so no new messages or server code. A closed tab is only noticed when LiveKit notices (about 20 s); Leave is near-instant. `npm test` now also runs `lib/*.test.ts`.
- Follow-the-speaker overlay (Showup 08): the compositor takes a list of camera sources (`addSource`/`removeSource`/`setVisible`), each with its own cut-out canvas, drawn at its real aspect ratio; the host's Mirror setting (default on) flips every ghost, host and guests, via one rule (`ghostsMirrored`), and only visible (or fading) sources are segmented, guests at most ~12 fps. `lib/presenter-overlay/speaker-follow.ts` is the pure, clock-free rule set for who is shown (sustained speech takeover, loudness margin, minimum dwell, silence keeps the last speaker, no-camera speakers ignored, pin, follow toggle); `components/presenter-overlay-control.tsx` samples the room every 100 ms and feeds it. `npm test` runs the unit tests (`node --test`). Size normalization (Showup 11): `lib/presenter-overlay/size-normalize.ts` (pure, clock-free) zooms each cut-out by how far its person sits from the camera (head-top to frame-bottom from per-row mask counts, gesture-stable; settles over ~10 s, ~1 s glide, capped 0.5–2.5x); host checkbox `normalizeSize`, default on, applies to all ghosts, `layoutGhosts` takes per-ghost zooms; the keep-background panel stays at zoom 1.
- Keep background (Showup 12): the host's own ghost can be a shaped panel (rounded/circle/arch, optional soft edge) instead of a cut-out. `lib/presenter-overlay/panel.ts` is the pure, clock-free part (crop-window size per shape, clamp to the camera frame, person bounds from the segmentation mask, target centre, `WindowSmoother` deadzone/dwell/glide, shape path builders); the compositor segments only ~4x/s to find the person in this mode. The circle is centred on the head estimated from the mask (no separate face detector). Guests are always cut out.
- Gestures (Showup 13): host-only, off by default. `lib/presenter-overlay/gestures.ts` (pure, clock-free: pose classification from MediaPipe hand landmarks, `GestureTracker` hold/grace/cooldown/smoothing, `cameraToOutput` fingertip mapping through the ghost's placement, mirror and panel crop) and `screen-zoom.ts` (`ScreenViewport`: 2x zoom toward a point, pan, reset, 400 ms glide, clamped to the screen). The compositor lazily loads the Hand Landmarker (model on storage.googleapis.com, already in the CSP), runs it on the host camera at ~14 fps (slower if it falls behind), zooms only the screen layer, and draws the laser dot on top; gestures only act while the host's own ghost is on the share. Reactions (Showup 20): thumbs up / thumbs down (four fingers curled, thumb clearly up/down; checked before the fist) held 400 ms, or a wave (`detectWave`: >=3 direction reversals over >=8% of the frame width within 1.5 s of open-palm wrist x) show 👍/👎/👋 by the top of the host's ghost via `reactions.ts` (`ReactionPlayer`: one at a time, 2 s, rises 15% of frame height; falls back to simple shapes without an emoji font); 3 s cooldown, a hold that finishes during it is used up; the palm reset now needs the wrist still, so a wave never resets the zoom. Spotlight (Showup 19): a raised fist (wrist above the lowest ~30% of the frame, tips tucked in; checked before pinch so a fist isn't read as a pinch) held 800 ms dims the screen (65%) except a soft circle (12% of frame height) on the middle of the hand, fading out over 500 ms; the host's Spotlight button is a sticky version (centred on the hand if one is in view, else the screen centre). Drawn after the screen layer, under strokes, ghosts and the laser. Air-draw (Showup 18): hold two fingers together ("pen" pose) to draw; `drawing.ts` (`StrokeBoard`, pure) keeps strokes in screen-content coordinates so they follow zoom/pan, holds ~2 s then fades over 1 s, caps at 2000 points; pen colour + Clear drawing in the host controls. Straight arrow (Showup 27): host toggle `arrowMode` makes the same pen pose draw a rubber-band arrow (`StrokeBoard` stroke `kind: "arrow"`: tail + latest fingertip only, dropped on finish if shorter than `MIN_ARROW_LENGTH`; `arrowHead` is the pure barb geometry; drawn by the compositor's `drawStrokes`). Shapes (Showup 29): a separate gesture, the "L" (index out, other fingers curled, thumb out >= 0.8 of hand size from the index knuckle and about square to the index; `classifyPose` returns `shape`, checked after pinch and before point; `SHAPE_HOLD_MS` 400) rubber-bands a box or ellipse from the fingertip's start point to its current position (`GestureState.shape`, host `shapeKind` setting Box/Ellipse; `StrokeKind` box/ellipse, two points, `MIN_SHAPE_SIZE` discard, `shapeBounds`). Line style (Freehand/Arrow) applies only to the two-finger pen. Pinned shapes (Showup 30; arrows too since Showup 33): boxes, ellipses and straight arrows never fade (`isPinnedKind`; `visible()` keeps them at alpha 1; `MAX_PINNED` 20, oldest dropped; freehand can't trim them), carry an optional label (boxes and ellipses only, `takesText`; `setText`, `cleanShapeText`, 80 chars; arrows are pinned quietly with no prompt but still appear in the list) drawn inside by the compositor via the pure `lib/presenter-overlay/text-fit.ts` (`textArea` = box, or the inscribed rectangle for an ellipse; `fitText` wraps and shrinks with an injected measure fn), and are removed by `remove`/`undoLast`/`clear`. The board's `version` lets the compositor tell the UI (`onShapes`, `onShapeFinished`) without diffing. Host UI is `components/shape-text-panel.tsx` (prompt after each shape: Enter adds text, Esc/No text keeps it plain, a new shape commits what was typed; list with remove and Undo; optional Document Picture-in-Picture pop-out, which must be opened by a click since PiP can't open from a hand gesture). They are fixed on the shared screen: they follow zoom and pan (screen-content coordinates) but not scrolling or changed content. Eraser (Showup 31): three fingers together (index, middle, ring extended and against each other, pinky curled; `classifyPose` returns `eraser`, after pen and before palm; `ERASER_HOLD_MS` 300; the reading's `middleTip` is the ring centre) wipes what a ring of `ERASER_RADIUS` (3.5% of screen height) touches: `StrokeBoard.eraseAt/eraseSwept` (pure; aspect-corrected; sweeps from the previous position so fast moves don't skip strokes; freehand and arrows anywhere along the line, boxes and ellipses only on their OUTLINE; strokes still being drawn are skipped; final, no gesture undo). The compositor draws a faint dashed ring on the stream while erasing. `onGesture` feeds a host-only indicator that is not drawn into the stream; Zoom in / Reset zoom buttons work without gestures.
- Guest pointer (Showup 14): guests can show a laser dot too. `lib/presenter-overlay/guest-pointer.ts` is the pure, clock-free part: strict messages on topic `showup-pointer` (guest -> host `pointer-request` and `pointer {u,v,on}`, host -> guest `pointer-status`), `GuestPointerBoard` (host setting "Guests can point" Off (default)/Ask me/On, approvals, per-guest revoke that works under any policy, 30 s request timeout, validation, ~33/s per-guest cap, dot times out 0.5 s after the last active message, smoothing, per-guest non-red colours), `PointerSender` (~13/s, one closing off) and `mapGuestPointer` (fingertip -> screen through the guest's ghost, same single mirror rule `ghostsMirrored`). Detection runs on the guest's device (`components/guest-pointer-control.tsx`: the shared Hand Landmarker + `GestureTracker` on their own camera; only the fingertip and an on/off flag are sent, lossy, to the host alone; hidden where MediaPipe can't run). The host status-pushes each guest (allowed only while their ghost is on the share, which includes a follow-the-speaker ghost, and the policy/approval allows it) from the 100 ms tick in `presenter-overlay-control.tsx`; the board ignores everything from a guest who isn't shown and permitted. The compositor's `setGuestPointers` draws each dot with the guest's name on their ghost (`placementFor(id)`). The host's Guest pointers list (permission, live pointing marker, Allow/Deny/Revoke) is host-only UI, never drawn into the stream. Guests have no zoom path: no message parses into one.
- Guest air-draw (Showup 22): guests can draw too, with their own host setting "Guests can draw" (Off default / Ask me / On) that is separate from "Guests can point". It reuses `GuestPointerBoard` (a second instance, sharing one colour map with the pointer board so a guest's stroke matches their dot) on its own topic `showup-draw` (`draw-request`, `draw {u,v,on}`, `draw-status`; `parseDrawToHost`/`parseDrawToGuest`). `components/guest-pointer-control.tsx` runs one detection loop on the guest's camera for both abilities (index finger = pointer, two fingers together = pen) and sends only the fingertip and a flag. `StrokeBoard` is owner-aware (host by default, guests by participant id; `begin/add/end(…, owner)`), a guest keeps at most `MAX_POINTS_PER_GUEST` (400) points so they can't use up the 2000 shared cap, and `clear()` clears every owner. The compositor's `setGuestPens` turns each pen tip into that guest's stroke via `mapGuestPenToScreen` (their ghost's placement and the single mirror rule, then the current zoom view, stored in screen-content coordinates so it follows zoom/pan) and ends it when the pen drops, the ghost leaves the share or drawing is revoked. The host's Guest drawing list (permission, live drawing marker, Allow/Deny/Revoke) is host-only UI.
- Co-ghosts (Showup 09): the presenter plus up to 2 guests (cap 3 ghosts) on the overlay, spaced along the bottom in the order added (`layoutGhosts` in the compositor; a lone ghost still follows the position setting). `lib/presenter-overlay/co-ghosts.ts` is the pure roster (consent flow, "Ask me"/"Let anyone join"/"Off" policy, 30 s expiry, drop on leave/camera-off with a grace period, longer for a camera that hasn't started yet); `overlay-protocol.ts` is the strict data-message format (topic `showup-overlay`, always addressed to one participant: `overlay-request`/`overlay-response`/`overlay-join-request`/`overlay-leave`/`overlay-state`). Presenter side lives in `presenter-overlay-control.tsx`; the guest side is `components/overlay-guest-control.tsx` (renders only while someone else is sharing and shows nothing of the presenter's settings). Guests only accept messages from the participant who is sharing. Follow-speaker is switched off while a guest is on and restored when the last leaves; while guests are on, who is speaking no longer picks the ghost even if the presenter re-enables it. Data messages need `canPublishData` (the main-room token leaves it at LiveKit's default, true; lobby tokens set it false).
- Lobby (Showup 07): optional, host-toggled. `lib/lobby.ts` (Redis: `showup:lobby:on:{digest}` flag, per-guest pending/approved/rejected/redeemed record with atomic Lua transitions, IP+identity block for 10 min after a reject). While the lobby is on, `api/rooms/join` returns a lobby-room token only (`showup-{digest}-lobby`: camera-only publish, no subscribe, no data), never a main-room token. Routes: `api/rooms/lobby` (host toggle + hidden subscribe-only host token), `api/rooms/lobby/decision` (host approve/reject), `api/rooms/lobby/redeem` (guest exchanges a one-time approval for a main-room token; polled as a fallback to the server-sent data message). UI: `components/lobby-host-panel.tsx` (ghost tiles, alerts, Document PiP), `components/lobby-guest-screen.tsx`. Lobby room names deliberately don't match `digestFromRoomName`, so the webhook ignores them. Rejection blocks by client IP, so anyone behind the same NAT is blocked with them for the block period.

## Environment

See `.env.example`. LiveKit is the shared self-hosted instance; Showup room names are prefixed `showup-`.

## Running locally

See `README.md`. Short version: start Redis (`docker run -d --name showup-redis -p 6380:6379 redis:7-alpine`), `cp .env.example .env.local` and add the LiveKit key/secret, then `npm run dev -- -p 3012`. LiveKit webhooks can't reach localhost, so `room_finished` cleanup and `egress_ended` recording readiness can only be tested on the VPS or through a tunnel.

## Deploying

`scripts/deploy-showup.sh` (repo root) builds `showup/`, pushes `fz96tw/showup-app` and recreates only the `showup` service on the VPS. The VPS stack is `vps/showup/` (own compose project, own `showup-redis` on its own network, joins the external `appnet`). The app must use `redis://showup-redis:6379`; on `appnet` the bare name `redis` is Nasiha's Redis. One-time setup and verification: `vps/showup/README.md`. A production-only CSP is set in `next.config.mjs`; if the overlay or LiveKit ever stops loading in production, check it first (MediaPipe needs `cdn.jsdelivr.net` for script/wasm and `storage.googleapis.com` for the model).
